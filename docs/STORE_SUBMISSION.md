## 4. نموذج Data Safety (إجابات جاهزة حرفيًا)

أجوبة نموذج «Data safety» في Play Console — تُنقل كما هي:

| سؤال النموذج | الإجابة الحرفية |
|---|---|
| Does your app collect or share any of the required user data types? | **نعم — نجمع** (Collect، لا Share) |
| نوع البيانات: Personal info | **Name, Phone number** |
| الغرض (Purpose) | **App functionality / Account management** — «تشغيل الحجز والإقامة والطلبات والمحادثة والفوترة» |
| هل البيانات **مشارَكة** مع أطراف ثالثة؟ | **لا — Data shared: لا شيء.** لا نشاركها مع أي طرف ثالث إطلاقًا |
| نوع البيانات: Financial info | **لا نجمع** — لا بيانات بطاقات؛ الدفع نقدي في الفندق (الفواتير تُدار داخليًا كأرقام تشغيلية لا كبيانات بطاقة) |
| نوع البيانات: Location / Contacts / Photos / Files / Identifiers… | **لا نجمع أيًّا منها** — لا معرفات إعلانات ولا موقع ولا جهات اتصال |
| Is data collected/processed in real time? | جزء تشغيلي (App functionality) — لا لقرار تقني مطلوب |
| Is data processing optional (user choice)? | رفع البيانات **ليس إلزاميًا**: الحجز والتطبيق يعملان بلا أي رفع بيانات إضافي عن الاسم/الهاتف الضروريين لتشغيل الحجز نفسه |
| Is data encrypted in transit? | **نعم ✓** — HTTPS لكل الاتصال |
| Can users request that their data is deleted? | **نعم ✓** — حذف عند الطلب عبر التواصل (انظر سياسة الخصوصية §6) |

> الدليل التقني: البيانات المجموعة = الاسم/الهاتف (حجز وبحث) + كود مُجزَّأ SHA-256 + سجلات إقامة/فوترة + رسائل/طلبات + سجل تدقيق؛ الإذن الوحيد في AndroidManifest هو `INTERNET`؛ لا Firebase ولا تحليلات ولا إعلانات (F3 مؤجلة).

## 9. خطوات التقديم (Google Play — مرقمة)

1. **(شرط مسبق)** إتمام أسبوعي F7 بلا SEV-1 وإقفال القائمة — إعلان مالك بوابة المتجر مفتوحة.
2. **إصدار بناء جديد من main:** تشغيل workflow `Mobile Release` (workflow_dispatch) أو دفع وسم `v*` → انتظر GitHub Release جديدًا بملفي APK (prod/dev) موقّعين بـ APP_VERSION المدمج.
   - **⚠ قرار تقني مطلوب قبل أول تقديم — التحويل إلى AAB:** Google Play **يطلب صيغة AAB للتطبيقات الجديدة** (منذ 2021)، بينما خط الإصدار الحالي يبني **APK** فقط (`flutter build apk` في mobile-release). خطوة التحويل المحفوظة: إضافة خطوة `flutter build appbundle --release --flavor prod` + اعتماد **Play App Signing** (المفتاح الحالي يصبح مفتاح رفع) + رفع `.aab` بدل `.apk` — تعديل سير عمل واحد بلا أي تغيير في كود التطبيق، لكنه **قرار تقني يوثَّق ويُنفَّذ بقرار قبل أول رفع** [يُستكمل بقرار المالك/التقني: تنفيذ خطوة AAB في mobile-release].
3. إنشاء **Release جديد** في Play Console (Internal testing → Closed → Production حسب رغبة المالك).
4. رفع الحزمة (AAB بعد القرار أعلاه) من أصول GitHub Release.
5. ملء نصوص القائمة (§3 — الاسم/الوصف المختصر/الوصف الكامل/الكلمات).
6. ملء **Data safety** بنصوص §4 الحرفية + رابط URL سياسة الخصوصية المنشورة (§2/بند 4).
7. رفع اللقطات (§7) + أيقونة التطبيق عالية الدقة (512×512) [يُستكمل بقرار المالك: أيقونة المتجر 512 — ملف `ic_launcher` الحالي مصدرها].
8. إكمال تقييم المحتوى (§5) والاستهداف (§6).
9. **تقديم المراجعة** ومراقبة بريد الدعم — زمن المراجعة خارج سيطرتنا (ذيل زمني موثَّق في الخطة §6.9).
10. عند الرفض: الرجوع فورًا إلى جدول §10 — كل الردود جاهزة.

### عناصر قرار المالك المفتوحة (ملخص)

1. بيانات الاتصال العامة (هاتف/واتساب/بريد/العنوان التفصيلي) — لنشرها في PRIVACY_POLICY وقائمة المتجر.
2. **URL العام لسياسة الخصوصية** (نشر نص `docs/PRIVACY_POLICY.md` على مسار عام).
3. نوع حساب Google Play (فردي/منظمة) + **بدء إجراء D-U-N-S مبكرًا** + بيانات السجل التجاري.
4. **قرار AAB:** تنفيذ خطوة بناء `appbundle` في mobile-release + اعتماد Play App Signing قبل أول رفع (متطلب Play الإلزامي للتطبيقات الجديدة).
5. أيقونة المتجر 512×512.
6. بلدان النشر الأولى + قرار فتح iOS (Apple Developer/TestFlight) بعد بوابة Play.
7. الشهادة الزمنية لأسبوعي F7 (البند الوحيد المفتوح في البوابة — §1).
