HOTEL PLATFORM — MOBILE APPLICATION PLAN

Guest App + Embedded Reception & Admin Dashboards

Document Type: Product, UX, Functional & Engineering Plan
Version: 1.0
Scope: MOBILE APPLICATION ONLY
Status: Execution Baseline
Primary Objective: Build a unified mobile application that serves three distinct personas through dynamic code-based authentication: (1) Guest with active stay, (2) Reception staff, and (3) Admin/Owner. The app must seamlessly integrate with the website booking engine, provide operational dashboards for staff, and deliver a complete guest experience during the stay.

0. EXECUTIVE DEFINITION

This mobile application is not a separate system.

This application is the mobile extension of the integrated hotel platform defined in PLAN-5.md.

The app serves three personas through the same codebase:

0.1 The Code-Based Authentication System

The application uses a unified code-based authentication system where different code types grant access to different personas:

Guest Access Code

· Generated at Check-In by Reception.
· Time-limited (active until guest checkout).
· Tied to specific Stay, Guest, and Room.
· Grants guest-level access only.
· Automatically expires at checkout.

Reception Access Code

· Generated by Admin.
· Time-limited (configurable, e.g., 8-hour shifts).
· Tied to specific Reception staff identity.
· Grants reception-level access.
· Can be revoked at any time.

Admin Access Code

· Generated by Master Admin.
· Time-limited (configurable, e.g., 24 hours).
· Tied to specific Admin identity.
· Grants full administrative access.
· Can be revoked at any time.

Website Booking Code (Tracking Code)

· Generated at Booking Creation on the website.
· NOT valid for app login.
· Used only for website reservation lookup.
· Expires after Check-In or after a defined period.

2. CORE PRODUCT PRINCIPLES

2.1 Unified Codebase, Multiple Personas

The same application binary serves all personas. Authentication via dynamic codes determines what the user sees.

```text
User Opens App
        ↓
Enter Access Code
        ↓
System Validates Code Type
        ↓
┌───────┴───────┐
│               │
▼               ▼
Guest Mode   Staff/Admin Mode
```

2.2 Code Lifecycle

Every access code has a lifecycle:

```text
┌─────────────────────────────────────────────────────────┐
│                    ACCESS CODE LIFECYCLE                │
│                                                         │
│  GENERATED → ACTIVE → USED → EXPIRED/REVOKED           │
│                                                         │
│  - Guest Code: Generated at Check-In, Expires at Checkout│
│  - Staff Code: Generated by Admin, Time-limited         │
│  - Admin Code: Generated by Master Admin, Time-limited  │
└─────────────────────────────────────────────────────────┘
```

2.3 Single Source of Truth

The mobile app is a client that consumes the central hotel platform API.

· All business logic resides in the backend/API.
· The app displays data, collects input, and shows results.
· No critical business rules are implemented in the app alone.
· The app never modifies data without server-side validation.

5. AUTHENTICATION — THE CODE SYSTEM

5.1 Code Generation

Guest Code

· Generated by Reception during Check-In.
· Format: H{6-digit-numeric}{2-char-checksum} (e.g., H834729X7)
· Tied to: stay_id, guest_id, room_id, hotel_id
· Validity: From generation until checkout or explicit revocation.
· Automatically expires at checkout.

Reception Code

· Generated by Admin.
· Format: R{6-digit-numeric}{2-char-checksum} (e.g., R492671M3)
· Tied to: user_id, role_id
· Validity: Configurable (default: 8-hour shift).
· Can be revoked at any time.

Admin Code

· Generated by Master Admin.
· Format: A{6-digit-numeric}{2-char-checksum} (e.g., A371849L9)
· Tied to: user_id, role_id
· Validity: Configurable (default: 24 hours).
· Can be revoked at any time.

Website Tracking Code (NOT for App)

· Generated by website booking.
· Format: HTL-2026-000421 (human-readable)
· Used only for website reservation lookup.
· Not valid for app login.

---

5.2 Code Validation Flow

```text
User Enters Code
        ↓
System Validates Format
        ↓
System Checks Code Against Database
        ↓
┌───────┴───────┐
│               │
Invalid         Valid
│               │
▼               ▼
Error         Check Expiry & Revocation
Message          │
        ┌───────┴───────┐
        │               │
      Valid           Expired/Revoked
        │               │
        ▼               ▼
    Determine      Show Error
    Code Type        Message
        │
┌───────┼───────┐
│       │       │
▼       ▼       ▼
Guest   Reception  Admin
Mode    Mode      Mode
```

---

5.3 Security Requirements

MUST

· Codes must be cryptographically secure (not sequential).
· Codes must have checksums to prevent typo-based collisions.
· Codes must be time-limited.
· Codes must be revocable.
· Multiple failed attempts must trigger rate limiting.
· Failed attempts must be logged.
· Code validation must happen server-side.
· Guest codes must be invalidated immediately at checkout.

MUST NOT

· Use predictable codes (e.g., incremental numbers).
· Allow brute-force guessing (rate limit).
· Expose code generation algorithm.
· Store codes in plaintext client-side.
· Allow code reuse after expiry.
· Allow admin/reception code to access guest data incorrectly.

18. FINAL PRINCIPLE

This mobile application is the operational backbone for guests during their stay and for hotel staff during their shifts.

It is built on one codebase with three distinct personas, connected by a secure dynamic code system that ensures:

```text
Right Person
    ↓
Right Code
    ↓
Right Context
    ↓
Right Data
    ↓
Right Experience
```

The app complements the website (which handles discovery and booking) and the reception dashboard (which handles operational work) to create a seamless hotel experience from booking through stay to checkout.
